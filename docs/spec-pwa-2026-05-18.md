**Date:** 2026-05-18
**Status:** Draft, pending review
**Owner:** Evolve admin server
**Related:** [spec-alert-subscriptions-2026-05-10.md](spec-alert-subscriptions-2026-05-10.md) (push delivery channel adds to the catalog there), [spec-alert-notifier-2026-05-09.md](spec-alert-notifier-2026-05-09.md)

## 1. Goal

Turn the existing Evolve admin web UI into a **Progressive Web App** so a single codebase serves three surfaces:

- **Desktop** (Mac, Windows, Linux) — installable to dock/start menu, own window, native notifications, offline last-known state.
- **Phone** (Android primary, iPhone with caveats) — installable to home screen, push notifications, responsive UI.
- **Tablet** (iPad, Android tablets) — same install path as phone, desktop-class layouts.

The web UI at `<pod>:5050` remains the canonical surface and stays available for platforms where the PWA install path is broken or undesired (e.g. shared machines, Linux distros without browser install support).

**The hard constraint:** a household-tech-capable operator (the "Plex test" — someone who can run Plex and Home Assistant but isn't a developer) must be able to install the app on their phone and laptop without reading docs.

**What we are not building:** a native desktop shell (Tauri/Electron), App Store distribution, or a multi-pod "generic" Evolve app. Each pod gets *its own* installed PWA — your pod is the product.

> **Update 2026-06-20 (reconciled with multi-pod):** the "no native desktop shell" line above was scoped to *this* PWA effort, and that scope still holds — the PWA is the **single-pod everyday surface** (install the *one* pod's dashboard as a desktop/phone app via the browser; per-pod, no central chooser). The "no native shell" decision was later **revisited and reversed for a different, complementary need**: operators running *multiple* pods. The multi-pod aspect (META:multi-pod, #3031) shipped exactly such a shell — the **"Evolve Pods" Tauri macOS app** ([../desktop/README.md](../desktop/README.md)): one app, one Dock icon, a tab per pod. It is not a "generic multi-pod PWA" (that remains a non-goal here) — it is a native shell that puts each pod's own admin UI in its own webview, preserving the per-origin pairing this spec relies on. Distribution (signing/notarization/auto-update) is milestone M2.6 and deferred ([spec-multipod-desktop-distribution-2026-06-19.md](spec-multipod-desktop-distribution-2026-06-19.md)). So §2 and §12 below are not in conflict with the Pods app: **PWA = per-pod single surface; Evolve Pods app = native multi-pod shell.** See [design-multi-pod-2026-06-11.md](design-multi-pod-2026-06-11.md) §3 (the hub / "one-app question") and §8.

## 2. Why PWA over native

| | Native shell (Tauri/Electron) | PWA |
|---|---|---|
| Codebase | New native shell + existing web UI | Existing web UI + ~3 small additions |
| Cross-platform | Mac built first; Windows/Linux/iOS/Android each a separate port | All platforms with one build |
| Distribution | Code signing, notarization, update server, ongoing certs | None — served by the admin server |
| Update flow | Auto-updater infrastructure to operate | Service worker fetches on next open |
| Offline | Full | Last-known state only (sufficient) |
| File drag-drop / paste (desktop) | Yes | Yes (standard web platform) |
| OS share-sheet target (mobile) | Yes | Android yes; iOS no (Safari gap) |
| Notifications | Full native | Web Push (works everywhere; iOS post-16.4 with caveats) |
| Menubar/tray | Yes | No |
| Host terminal | Yes (PTY) | No host-shell; *but the meaningful terminal is on the mini, not the laptop* — same WebSocket pattern works fine |
| Keychain | OS keychain | Browser credential manager + Passkeys |
| Build effort (v1) | 4–6 weeks Mac-only, 8–12 cross-platform | 4–7 weeks across all platforms |
| Maintenance | 2–4 days/month, indefinite | Effectively zero beyond normal web UI maintenance |
| Apple risk | App store rules apply | iOS PWA support is second-class; reversible escape hatch by adding a native iOS shell later |

The PWA path covers desktop + mobile + tablet with one codebase. Native becomes a possible *later* upgrade for menubar presence or keychain, only if real demand emerges.

## 3. Architecture

### Per-pod PWA model

Each pod's admin server serves its own manifest, icons, and service worker. The operator visits `https://<their-pod>/` from their phone or laptop, clicks Install, and gets a PWA bound to that pod. There is **no central evolve.app PWA** that pairs to a pod after install — that would introduce a configuration step the per-pod model avoids.

Implication: a household with two pods (rare today, possible in future) installs two PWAs. That's the right behavior — they're independent products.

### Files added to the admin server

```
packages/admin/evolve_admin/web/
├── static/
│   ├── manifest.json           ← rendered per-pod (pod name from network.json)
│   ├── sw.js                   ← service worker (cache + push handler)
│   ├── icons/                  ← 192px, 512px (maskable), apple-touch-icon
│   │   ├── icon-192.png
│   │   ├── icon-512.png
│   │   ├── icon-512-maskable.png
│   │   └── apple-touch-icon-180.png
│   └── push-sw-register.js     ← installs the SW + handles push subscribe
├── templates/
│   └── base.html               ← adds <link rel="manifest">, <meta> tags, iOS install hints
└── server.py
    └── + routes for: /manifest.json, /sw.js, /api/push/{subscribe,unsubscribe,vapid-public-key}
```

### Manifest (rendered per-pod)

```json
{
  "name": "Evolve · {pod_name}",
  "short_name": "{pod_name}",
  "description": "Your Evolve pod",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#0d1117",
  "theme_color": "#0d1117",
  "icons": [
    {"src": "/static/icons/icon-192.png",  "sizes": "192x192", "type": "image/png"},
    {"src": "/static/icons/icon-512.png",  "sizes": "512x512", "type": "image/png"},
    {"src": "/static/icons/icon-512-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable"}
  ]
}
```

`pod_name` derives from `network.json::pod.name` (already exists); if absent, falls back to `"Evolve"`.

### Service worker responsibilities

Single `sw.js`, kept deliberately small:

1. **Offline shell cache.** On first install, precache the app shell (HTML, JS bundle, CSS, icons). On subsequent fetches, network-first with a cache fallback so the app opens to last-known UI when the mini is unreachable.
2. **Push event handler.** Receives push payloads from the mini's dispatcher, renders an OS notification.
3. **Notification click handler.** Opens the relevant admin-UI page (deep link from the push payload).
4. **Version banner.** On update detected, surfaces "New version available — refresh" in-app rather than auto-reloading mid-task.

No background sync, no Workbox, no fancy caching strategies in v1. The mini is the source of truth; the SW exists to make the app installable and to receive pushes.

### Mobile access — how phones reach the pod

A pod served at `https://<pod>.<tailnet>.ts.net` is reachable only by devices on the tailnet. For mobile users, that means the phone needs to be on the tailnet — Tailscale's mobile app handles this.

| Path | What the user does | Tradeoff |
|---|---|---|
| **Tailscale mobile app (default)** | Install from App Store / Play Store, sign in to the same tailnet as the laptop. | One-time 2-min setup per device; after that the phone joins the mesh transparently. Free. Matches the laptop-side setup users already accept. |
| **Tailscale Funnel (opt-in)** | No phone install; pod gets a publicly reachable URL via Tailscale's relay. | Admin UI becomes publicly reachable; auth becomes load-bearing. Useful for delegating access to non-Tailscale collaborators, but not the default. |

**Recommend Tailscale-on-phone as the default.** Mature mobile clients, same trust model as the laptop install, no public exposure. Self-hosted-services peer-group (Home Assistant, Plex, Synology) already uses this pattern — the audience expects it.

**Funnel is a v2 opt-in.** Surface it in the setup wizard with a security warning attached. Never the default.

### Push notifications survive a disconnected phone

A useful property worth surfacing in user-facing copy: **Web Push doesn't require the phone to be on the tailnet to receive notifications.** The subscription is registered once (when the phone is connected); after that, the mini sends pushes through Apple's / Google's / Mozilla's push infrastructure, which delivers to the phone over any network.

- **Receiving alerts** — works on cellular, public Wi-Fi, anywhere the phone has internet. No Tailscale required.
- **Opening the PWA to see details** — tapping the notification opens the PWA, which then loads from the mini and needs the tailnet again.

Mitigation for the open-PWA-needs-tailnet case: pack enough information into the push payload (header, body, severity, suggested fix) that the notification itself is meaningful without drilling in. The catalog event-body templates from [spec-alert-subscriptions-2026-05-10.md](spec-alert-subscriptions-2026-05-10.md) already work this way — same templates render the push payload.

This makes mobile push genuinely useful even for users whose phones aren't always on the tailnet (e.g. parents who only enable Tailscale at home, or users on cellular plans that block VPNs intermittently).

## 4. Phase 0 — prerequisites (do regardless)

These are required for the PWA to work *and* are healthy improvements to the existing web UI on their own. They land first, independent of the PWA decision.

### 4.1 HTTPS on the LAN

Service workers require HTTPS (or localhost — which doesn't help when accessing from a phone over Tailscale). Three options:

| Option | Pros | Cons | Recommendation |
|---|---|---|---|
| **Tailscale-issued certs** (`tailscale cert`) | Free, real LetsEncrypt cert for `<host>.<tailnet>.ts.net`, auto-renewed by Tailscale, works on every device once on the tailnet | Tailscale-coupled (we already are, but worth flagging) | **Default.** |
| **Caddy with local CA** | Independent of Tailscale | Requires installing root CA on every device — fails the Plex test | Skip. |
| **mkcert** | Easy dev cert generation | Same root-CA problem on devices | Dev-only. |

**Work involved:**
- Run `tailscale cert <hostname>.ts.net` during setup; renew via cron or Tailscale's daemon.
- Put Caddy in front of the admin server on port 443, terminating TLS with the Tailscale cert and proxying to `127.0.0.1:5050`.
- Update `network.json::adminBaseUrl` to the `https://` URL.
- Audit every place in the codebase that emits an admin-UI link (alert messages, setup wizard output, etc.) to use `adminBaseUrl` instead of hardcoded `http://...:5050`.

Estimate: **3–5 days**, including audit and Caddyfile templating into the setup wizard.

### 4.2 Stable URL pattern per pod

A PWA's `start_url` is bound to an origin. We need a consistent, stable URL per pod that:

- Has a valid TLS cert (Phase 0.1 covers this).
- Doesn't change when the operator re-deploys or renames the mini.
- Is what every operator-facing link in the system uses (no more bare `http://team-bot-a-mini:5050`).

`network.json::adminBaseUrl` already exists and resolves to `https://<host>.<tailnet>.ts.net` after Phase 0.1. Codify it as the single source of truth — `evolve_admin.config.resolve_admin_base_url()` helper, called everywhere a URL is emitted.

Estimate: **1–2 days** for the audit + helper + replacing call sites.

### 4.3 Responsive design audit

The admin UI was built desktop-first. For phone/tablet to be a real surface (not just "the desktop UI shrunk"), every primary page needs a pass at ≤360px width.

Pages to audit:

- Home / dashboard
- Bots (list + per-bot detail)
- Apps
- Alerts (Active / History / Subscriptions)
- Proposals
- Cost
- Config
- Maintenance / Diagnostics
- Setup wizard (when reached via web)

Audit checklist per page:

- [ ] Renders at 360px without horizontal scroll.
- [ ] Tap targets ≥44px (Apple HIG) / 48dp (Material).
- [ ] No hover-only affordances (touchscreens don't hover — every "hover to reveal" becomes "tap to expand" or always-visible).
- [ ] Tables either responsive (card layout below ~640px) or horizontally scrollable with a visible scroll indicator.
- [ ] Nav usable on phone (probably: hamburger or bottom-tab pattern below ~640px).
- [ ] Forms readable, inputs full-width on phone.
- [ ] Modals fullscreen on phone.

This is the **single biggest piece of Phase 0** and the work least specific to PWA — it's just "make the admin UI mobile-usable." A PWA install on phone that opens to a desktop layout would fail the Plex test immediately.

Estimate: **1–2 weeks** depending on current state. Worth a dedicated sub-spec if it's >2 weeks once scoped.

### 4.4 Cross-browser baseline

Today's QA is presumably Chrome on Mac. Establish a test matrix:

| Browser | Surface |
|---|---|
| Chrome (Mac/Windows/Linux desktop) | Primary install target |
| Safari (macOS) | Mac install fallback |
| Safari (iOS/iPadOS) | iPhone/iPad install — rough edge, see §7 |
| Chrome (Android) | Android install — best mobile experience |
| Firefox (desktop) | Compatibility, no install |
| Edge (Windows) | Chromium-based, should "just work" with Chrome target |

Estimate: **1 day** to set up + initial pass; ongoing as part of normal QA.

### 4.5 Phase 0 totals

- HTTPS on LAN: 3–5 days
- URL pattern: 1–2 days
- Responsive design audit + fixes: 1–2 weeks
- Cross-browser baseline: 1 day

**Total Phase 0: 2–3 weeks.** Most of which is the responsive audit. Note that all of this is value-positive *even if the PWA doesn't ship* — it makes the existing web UI work on phones over Tailscale.

## 5. Phase 1 — minimum viable PWA

After Phase 0, the actual PWA work is small.

### 5.1 Manifest + icons

- Add `/manifest.json` route, renders the per-pod manifest.
- Add `<link rel="manifest" href="/manifest.json">` to the base template.
- Generate icon set (192/512/512-maskable/apple-touch-icon). Use Evolve's existing logo asset; generate the maskable variant with the standard safe-area padding.
- Add iOS-specific meta tags: `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title`.

### 5.2 Service worker

- Add `/sw.js` route serving the SW file (must be served from origin root or a path covering the app — top level is simplest).
- Register the SW from a script in the base template (`navigator.serviceWorker.register('/sw.js')`).
- Implement offline shell cache: precache the app shell on `install`, network-first with cache fallback on `fetch`.
- Implement update flow: on new SW detected, post a message to clients; admin UI surfaces a "New version available — refresh" toast.

#### 5.2.1 Deploy-safety contract (added 2026-06-20 after a fleet-promote lockout)

A routine canary promote locked an operator out of the admin UI: the
browser's registered SW served a **stale cached app shell** that
referenced JS/CSS assets the new release had renamed, and its fetch
handler then resolved `respondWith` with `undefined` for the navigation
(`caches.match('/')` on an empty cache) — which throws *"FetchEvent.respondWith
received an error: TypeError: Load failed"* and blanks the shell. A
server-side release rollback did **not** fix it (the SW lives in the
browser); only clearing site data did. A fresh incognito window (no SW)
loaded the same release fine.

The SW must therefore satisfy three invariants so a deploy can never lock
out an existing session, and a hard-broken state self-heals on reload:

1. **Fail-open fetch.** The handler never hands `respondWith` a value
   that blanks the page — no `undefined`, no `Response.error()` for a
   navigation. When network and cache both miss, it re-issues the network
   request (which, if it also fails, rejects `respondWith` → the browser's
   native, reload-recoverable error page) rather than a synthetic blank.
2. **Per-build cache, flushed on activate.** The server stamps the SW's
   `CACHE_VERSION` with a hash of **all** SPA assets (index.html + the
   `js/{core,pages,widgets}` + `css` modules — not just index.html, since
   the shell references modules by stable filename and a module-only PR
   leaves index.html byte-identical). `activate` deletes every cache that
   isn't the current build's, so a deploy can never serve a prior build's
   shell/modules.
3. **Self-heal.** `install` calls `skipWaiting()` and `activate` calls
   `clients.claim()`, so a fixed/new SW takes over on the **next reload** —
   a blanked tab (which can't click the update toast) recovers without
   manual cache-clearing.

Proof: `packages/admin/tests/test_sw_fetch_behavior.py` (drives the real
`sw.js` through these scenarios) + `test_sw_shell_fingerprint.py` (asset
fingerprint + cache-version stamping).

**Operator emergency workaround** (if a browser is ever stuck on a blank
admin shell and a reload doesn't recover it): open the pod URL in a
private/incognito window to confirm the server is healthy, then in the
normal window go to **DevTools → Application → Service Workers →
Unregister**, click **Clear site data**, and reload. On mobile, "clear
website data" for the pod's origin in the browser settings does the same.

### 5.3 Install UX

- Listen for `beforeinstallprompt` event (Chrome/Edge/Android), surface a "Install Evolve" button in a tasteful spot (probably the user menu, not a banner).
- For iOS Safari: detect iOS Safari + non-standalone mode, show a one-time "Add to Home Screen via Share → Add to Home Screen" hint with a screenshot. Dismiss permanently after first dismissal or after detecting standalone mode.

### 5.4 File drop and paste (desktop)

Desktop users get a familiar Slack/Linear-style flow for getting screenshots and files into Evolve. No PWA-specific machinery required — these are standard web-platform features that work in any browser, but the PWA's standalone window makes them feel like a native app.

- **Drop zones** on the evo chat drawer, per-bot conversation pages, and the Diagnostics page. Drag-over feedback (highlight the target). On drop, file uploads via the existing chat-message endpoint with an inline preview before send.
- **Paste handler** on the same surfaces. Cmd+V / Ctrl+V with a screenshot in the clipboard delivers the image as a Blob; same upload path as drop.
- **Accepted types** for v1: images (png, jpg, gif, webp), text (txt, log), JSON. Reject + warn on others until a real need surfaces.
- **Max size** ~10MB per file in v1 (caps the upload buffer; screenshots and logs fit comfortably).

The mobile share-sheet equivalent (Web Share Target API) is **deferred** — iOS Safari doesn't support it, and Android-only feature parity isn't worth the carry. Mobile users paste or use a file picker button on the same drop zones. Revisit when iOS adds support.

Estimate: **2–3 days**.

### 5.5 What "v1 PWA installed" gives the operator

- Standalone window, no browser chrome, own dock/launcher/home-screen icon.
- Opens to last-known state if mini unreachable.
- Visible "New version available" prompt instead of stale assets.
- Drag-and-drop and paste of screenshots/files into chat and diagnostics surfaces.
- Phone and tablet operators can install too — same code path.

Estimate: **5–8 days** total for Phase 1 (3–5 days for §5.1–5.3 + 2–3 days for §5.4).

## 6. Phase 2 — push notifications

This is the single highest-value feature the PWA adds. It depends on the alert-subscriptions catalog from [spec-alert-subscriptions-2026-05-10.md](spec-alert-subscriptions-2026-05-10.md) — PWA push becomes a **new delivery channel** alongside the existing Slack/Telegram/Discord channels in that spec's dispatcher.

### 6.1 VAPID setup

- Generate per-pod VAPID keypair at setup time, store private key under `{shared_dir}/push/vapid.json` (evolve-owned, 0600).
- `GET /api/push/vapid-public-key` returns the public key for the PWA to use during subscription.

### 6.2 Subscription flow

```
PWA                                  Admin server
 │                                    │
 │ register service worker            │
 ├───────────────────────────────────►│
 │ ◄──────── SW installed ────────────┤
 │                                    │
 │ user enables push on Alerts page   │
 │ (browser permission prompt)        │
 │                                    │
 │ pushManager.subscribe(VAPID pubkey)│
 │ ──► browser returns endpoint URL   │
 │                                    │
 │ POST /api/push/subscribe           │
 │   {endpoint, keys: {p256dh, auth}, │
 │    device_label: "Pod-Admin iPhone"}   │
 ├───────────────────────────────────►│
 │                                    │ write to {shared_dir}/push/subscriptions.json
 │ ◄────── 200 OK + subscription_id ──┤
```

### 6.3 Subscription storage

`{shared_dir}/push/subscriptions.json`:

```json
{
  "version": 1,
  "subscriptions": [
    {
      "id": "sub_a1b2c3",
      "endpoint": "https://push.apple.com/...",
      "keys": {"p256dh": "...", "auth": "..."},
      "device_label": "Pod-Admin iPhone",
      "user_agent": "Mozilla/5.0 ...",
      "created_at": "2026-05-18T10:00:00Z",
      "last_delivery": "2026-05-18T12:34:00Z",
      "last_failure": null
    }
  ]
}
```

Atomic temp+rename writes. Owned by the `evolve` user (same pattern as other shared-dir state).

### 6.4 Integration with the alert dispatcher

The alert-subscriptions catalog gains a new delivery channel:

- Today's channels: `slack`, `telegram`, `discord` (the openclaw subprocess routes).
- New: `pwa_push` — the dispatcher, when fanning out a catalog event with severity ≥ subscriber's threshold, also POSTs a push payload to every registered PWA subscription.

The Subscriptions UI from the alert-subscriptions spec gains a top-level "Send to:" row that the operator can multi-select: Telegram + PWA push, or PWA push only, etc.

### 6.5 Sending pushes

Use `pywebpush` (mature, well-supported) on the mini. The dispatcher's send path:

```python
def _send_pwa_push(event_key: str, payload: dict, subscription: dict) -> SendResult:
    try:
        webpush(
            subscription_info={"endpoint": subscription["endpoint"], "keys": subscription["keys"]},
            data=json.dumps({"event_key": event_key, "title": ..., "body": ..., "url": ...}),
            vapid_private_key=load_vapid_private(),
            vapid_claims={"sub": "mailto:evolve@pod.local"},
        )
        return SendResult.SENT
    except WebPushException as e:
        if e.response.status_code == 410:  # Gone — subscription invalidated
            mark_subscription_gone(subscription["id"])
        return SendResult.FAILED
```

### 6.6 Service-worker push handler

```js
self.addEventListener('push', (event) => {
  const data = event.data.json();
  event.waitUntil(
    self.registration.showNotification(data.title, {
      body: data.body,
      icon: '/static/icons/icon-192.png',
      badge: '/static/icons/badge.png',
      data: { url: data.url, event_key: data.event_key },
      tag: data.event_key,  // collapse repeats of the same event type
    })
  );
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow(event.notification.data.url));
});
```

### 6.7 iOS-specific caveats

- iOS Safari only delivers Web Push to PWAs added to the home screen (iOS 16.4+).
- The UX surface for "you need to add this to home screen first" is the iOS install hint from Phase 1.3 — push toggle on Alerts page detects "iOS not-yet-installed" and surfaces the hint inline.

Estimate: **1 week** including UI wiring, dispatcher integration, and iOS testing.

## 7. Phase 3 — embedded mini terminal

Per the user's requirement: this is a terminal **on the mini**, not on the operator's machine. That removes the hardest part (host-shell PTY from a browser) and reduces this to "embed a terminal that WebSockets to the mini."

### 7.1 Approach

- Run `ttyd` (or write a small Python equivalent using `ptyprocess` + WebSockets — likely cleaner than a third-party dep) on the mini, bound to `127.0.0.1`.
- Admin server proxies `wss://<pod>/api/terminal` to the loopback ttyd, gated by the existing admin-UI auth.
- Embed `xterm.js` in a new admin page (or modal); WebSocket connects through the admin server.
- The terminal runs as the `evolve` user, with sudo grants per the existing sudoers rules.

### 7.2 Security model

This gives anyone with admin-UI access a shell on the mini. That's already true via SSH, but it's more discoverable through the UI, which means:

- First-use warning modal: "This opens a real shell on your mini. Commands run here can change your pod's configuration."
- Audit log: every command typed gets appended to `{shared_dir}/terminal/audit-<date>.jsonl`.
- Optional config: `terminal.enabled` defaults to `true` for the primary user, but ops can disable in `network.json`.

### 7.3 Tier-aware launch hint

For commands that want to be run on the user's *laptop* (rare — most things are mini-side), the terminal-page header carries a note: "This terminal runs on your mini. For laptop-side commands, open your local terminal app."

Estimate: **3–5 days**.

## 8. Phase 4 — tunnel CONNECT helper

When the PWA can't reach the mini, it should help the user re-establish the tunnel rather than show a generic network error.

### 8.1 Detection

Service worker catches fetch failures; admin UI shows a "Tunnel down" full-page state instead of a broken-looking screen.

### 8.2 CONNECT button options

In rough order of usefulness:

1. **Deep-link to Tailscale app** (iOS/Android/macOS) — `tailscale://` URL scheme. Most users on macOS have the Tailscale app; this opens it.
2. **Tiny local helper binary** (`evolve-helper`) — installed on user's laptop (one-line install: `brew install evolve-ops/tap/evolve-helper`). Runs on `127.0.0.1:5051`. PWA pings it; helper runs `tailscale up`. Optional for users who want one-click connect; defaultable to off.
3. **Platform-specific instructions** — fallback for everyone else. "Open Tailscale on your phone and make sure it's connected."

### 8.3 v1 scope

Phase 4 v1 is **option 1 + option 3 only.** The local helper (option 2) is a real native artifact with all the signing/distribution issues a full desktop app has, and we're explicitly avoiding those. Defer to a follow-on if there's demand.

Estimate: **2 days**.

## 9. Phase 5 — setup wizard inside the PWA *(deferred)*

The user's original motivation included "help with setup when launched." For a PWA, setup is the chicken-and-egg case: the PWA is served by the admin server, so to use the PWA for setup you must first have a running admin server.

Two paths:

**Path A: separate `evolve-installer` web server.**
- Tiny standalone Python script runs on the mini during fresh setup, serves a localhost-only setup PWA on `:5051`.
- User SSHes to the mini, runs `sudo evolve-admin setup`, then opens `http://localhost:5051` from the laptop (through Tailscale once Tailscale is up).
- Installer hands off to the real admin server once it's running, then exits.

**Path B: keep CLI setup, PWA only for post-setup.**
- Setup remains `sudo evolve-admin setup` on the mini terminal (today's flow).
- PWA shows up after the admin server is running.
- The PWA's terminal (Phase 3) makes "SSH to mini" unnecessary for *re-setup* and routine ops — only the first install needs SSH.

**Recommendation:** Path B for v1. The "first 5 minutes" setup story is its own design problem (mini OS install → Tailscale auth → evolve-admin setup → PWA install on phone) and deserves its own spec. Don't entangle it with PWA shipping.

Estimate: **deferred** (own spec).

| 3 | Embedded mini terminal | 3–5 days | Phase 0 |

**Total to feature-complete v1: ~4–6 weeks.**

Phases 1–4 can land in any order after Phase 0. Push (Phase 2) is the highest-value follow-on and should go first. Terminal (Phase 3) and tunnel CONNECT (Phase 4) are parallelizable.

## 11. Open questions for review

1. **Tailscale coupling.** Phase 0.1 makes us reliant on Tailscale-issued certs. If a household wants to use a different mesh VPN (Nebula, Headscale, ZeroTier), we'd need a documented alternate path. Acceptable for v1? My take: yes, document Tailscale as the supported default, note alternates in setup docs but don't engineer for them.

2. **Pod-name URL stability.** If an operator renames their mini (`<old>.ts.net` → `<new>.ts.net`), the installed PWA breaks (origin mismatch). Options: (a) accept it — uninstall + reinstall; (b) emit a "pod URL changed" pre-deploy warning. Recommend (a) for v1; renames are rare and the cost of re-install is small.

3. **Per-device vs. per-user push subscriptions.** If Pod-Admin installs the PWA on phone + laptop, do all alerts fan to both devices, or does the user pick one? Recommend: fan to both, with a per-device disable toggle on the Alerts → Subscriptions tab. (Operators with one device pay nothing for the multi-device case.)

4. **Push notification permission timing.** When do we ask? Asking on first page load is hostile (deny-by-reflex). Recommend: only when the operator enables push for a specific event type on the Subscriptions tab — by which point intent is clear.

5. **Service worker update strategy.** `skipWaiting` (new SW immediately replaces old) vs. version-pinned (operator must refresh). Recommend skip-waiting + an in-app toast ("New version active") for everyday updates; reserve "Reload to update" prompts for breaking changes.

6. **iOS install hint discovery.** iOS users won't get a browser install prompt and may never learn the PWA can be installed. Where do we surface the hint? Recommend: a small banner on first visit from iOS Safari, dismissible, plus a permanent "Install" item in the user menu.

7. **Member-bot users.** This spec is sysadmin-only. The member-bot users (Slack/Discord/Telegram-end-users) already get push via their chat platform. Worth a follow-on spec to give member bots their own PWA per [spec-evo-wizard-2026-05-05.md](spec-evo-wizard-2026-05-05.md)? Note but don't scope here.

8. **Terminal page placement.** Where does Phase 3's terminal live in the IA? Dedicated page, or modal launched from a "wrench" icon? My take: dedicated page under Maintenance or a top-level "Terminal" item — modal feels too transient for a real shell.

9. **Cert renewal failure modes.** Tailscale certs are 90-day LetsEncrypt; renewal is automatic but can fail silently. The admin server should monitor cert expiry and emit an Alerts-page Signal at <14 days remaining. Counts as Phase 0 work or its own follow-on?

## 12. Out of scope

- **Native desktop shell (Tauri/Electron).** Possible later upgrade if menubar presence or keychain demand justifies it. Not v1.
- **App Store distribution** (Mac App Store, iOS App Store, Google Play). PWAs deliberately sidestep these.
- **Generic multi-pod evolve.app PWA.** Each pod owns its own PWA install; no cross-pod chooser.
- **Member-bot push surfaces.** Sysadmin-only; member bots use their chat platforms' native push.
- **Offline write actions.** Service worker caches reads only. Writes that fail offline show "mini unreachable" rather than queueing for later replay. Replay is a real feature but a separate design problem.
- **Hosted notification fallbacks** (SMS via Twilio, email push). The alert-subscriptions spec also defers these.
- **Background sync / periodic sync.** No background work happens in the SW beyond push receipt.

## 13. Why this is the right shape

- **Three surfaces, one codebase.** Desktop, phone, tablet all installable from the same per-pod web UI. Mobile becomes a real audience without a separate mobile app track.
- **Highest-value feature gets ahead.** Push notifications to phone is the single biggest UX improvement; it sits at Phase 2, blocked only by Phase 1 plumbing.
- **Phase 0 is value-positive on its own.** HTTPS + responsive UI + URL hygiene are improvements to the existing web UI regardless of whether the PWA ever ships. Low regret.
- **No app store dependency.** Distribution is via "visit your pod URL and click Install" — fits the "your pod is the product" framing and dodges Apple/Google review queues.
- **Native escape hatch is preserved.** If iOS PWA limits prove blocking, a thin native iOS shell can be added later without rebuilding the web UI. Same for Mac if menubar presence becomes critical.
- **Plex-test compatible.** The install path is "visit URL, click Install" on every supported platform. The dropoff cases (iOS share-sheet, Tailscale not running) get explicit UI rather than confusing browser errors.
