the code to the claims, then make the central claim demonstrable, then harden.*

(~80% shipped) whose headline "recursive self-improvement" claim does not yet

operational learning, not algorithms. None of the gaps are dead ends.

verify to confirm the gap is closed. A roadmap item without a falsifiable proof
artifact is just a wish (which is, fittingly, the same standard the product holds
its own proposals to).

## Phase 4 — Maintainability & strategic decoupling *(ongoing + one larger bet)*

> Mostly hygiene, plus the one genuinely strategic item that lifts the market cap:
> getting off single-platform lock-in.

> **Agent-legibility doctrine (adopted 2026-06-10).** The bar for code structure
> is not human readability — it is *agent legibility*, because LLM agents are and
> will remain the primary coding mode here:
> 1. **Bounded context per change** — any unit of work must fit in a modest
>    context window together with everything needed to edit it safely. Oversized
>    files are a tax paid on every touch, scaling with churn.
> 2. **Verifiers over readability** — agents improve by iterating against
>    machine feedback (types, tests, ratchet lints), not by reading nicer code.
> 3. **One canonical copy of every primitive** — duplicates absorb bug fixes and
>    act as conflicting few-shot examples that teach agents the wrong pattern.
> 4. **Locality beats abstraction** — a 600-line function that does one coherent
>    thing top-to-bottom is fine; deep indirection, DI towers, and aesthetic
>    50-line-function rules make agent navigation *worse*. No blanket
>    readability passes over the cold long tail.
>
> **Exception:** privileged paths (sudoers renderer, appliers, install exec,
> auth) are held to human **auditor-grade** readability — outside security
> reviewers and deeper diligence *will* read those line-by-line.
> Decomposition is prioritized by **churn × hazard, never size alone**, and any
> file move must update the docs-corpus file:line anchors in the same PR — the
> anchor accuracy is what makes agents effective in this repo at all.

## Sequencing logic

- **Phase 0 first, always** — it's nearly free and it's what a reviewer reads.
- **Phase 1 is the bet** — everything else is table stakes; this is the thesis.
  Do it before Phase 2–4 because a closed optimizer loop changes what "hardening"
  is even protecting.
- **Phases 2/3 in parallel** once 1 is underway — independent tracks, separate PRs.
- **Phase 4.3 (adapter seam) is the only large strategic item** — schedule it
  deliberately while the coupling surface is still small; it gets more expensive
  every week.
- **Phase 5 anytime** — independent, cosmetic, good for momentum between hard phases.
- **1.7 starts immediately** — it's wall-clock-bound, not effort-bound; every week
  it isn't running is a week the headline claim stays test-only.
- **Phase 2 residuals (2.6–2.11) next among the security work** — they are the gap
  between "shipped something" and Phase 2's own exit criterion, and 2.6/2.7 are the
  two most quotable open findings.
- **Phase 6 before Phase 7** — packaging + toolchain make the store/deploy work
  (and every other refactor) safer and cheaper; both before any Phase 8 build-out.
- **Phase 8.1 (research) can run anytime** — it's read-only; 8.2/8.3 wait on its
  recommendation and on 4.3 C.
- **All decomposition work follows the agent-legibility doctrine** (Phase 4
  intro): churn × hazard picks the targets, privileged paths get the
  auditor-grade bar, and nothing is split for aesthetics. Within Phase 6,
  dedup (6.2) and the type-check ratchet (6.3) outrank any splitting — they
  are the highest quality-per-effort items for LLM-mode coding.

Each row above is a self-contained PR. Per the team's working style:
non-destructive changes (docs, redaction, tests, stubs) land and auto-merge;
behavior-changing security/RSI work (0.3, 0.6, 1.x, 2.x) gets a build-then-review
pass before merge.
