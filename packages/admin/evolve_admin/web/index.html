Forge Jobs

Track and approve forge runs for App Gallery installations and improvements.
How it works
The forge turns an app idea into a running app. Every app starts with a manifest — its spec, file list, and tests — that comes from a Gallery template, an Evo chat, or an RSI proposal. The bot drafts the code (using its own LLM), critiques its own work over a few rounds, runs the app's tests, then either you approve it or — when the request was already a deliberate conversation — it ships automatically. The manifest is updated at the end so it always reflects what's on disk.

        How users and identity work in Evolve
        

          
Three separate identity concepts live on this page. They share words but mean different things:

          
    
            
  • Pod admins (the first card) — users whose Telegram/Slack/Discord/WhatsApp IDs are granted admin privileges in every multi-user bot's chat. Independent from the Unix admin (in Settings → Pod Config). Required to use evo's chat surface as an admin.
    • 
            
  • Per-bot owners (in each bot's panel) — for each bot, the messaging identity of its owner. Owners get alert delivery, self-claim privileges, and (on multi-user bots) sole primary-user status. Independent per bot.
    • 
            
  • Per-bot paired users (also in each bot's panel) — the channel-side allowlist of who can actually message the bot. Pending pairing requests appear here for approval; known pod admins auto-approve.
    • 
          

          
Glossary:

          
    
            
  • external_id — the platform's stable user identifier (Telegram chat_id, Slack user id like U…).
    • 
            
  • Person ID (wire name pod_user) — a stable label that ties multiple channel identities to one human. Optional, but required if you want to attach a display name or revoke a person across channels at once.
    • 
            
  • Display name — a human-readable label shown in this UI. Attached to the Person ID. Telegram/Slack users have their platform names auto-discovered when possible.
    • 
          

        

      


      
      


      
      

        
Pod Admins (messaging)

        

          Anyone listed here gets admin privileges on every multi-user bot's chat surface — runs commands like evo, can use evo's tool surface, bypasses per-user gates. Independent from the Unix admin in Settings → Pod Config. Add an admin by entering their channel + ID (Telegram numeric, Slack U…); we'll try to auto-discover their username after.

Self-claim Passphrases

        

          Alternative to typing IDs above: send a passphrase out-of-band, and the recipient messages any bot with that word to record themselves. The admin passphrase grants pod-wide admin; the primary passphrase grants per-bot owner status on whichever bot they sent it to. Saying both in one message claims both at once.

Backup

      

        Cloud backup pushes eligible data to a private GitHub repo so you can recover from drive loss, theft, or a host swap. Local backup (Time Machine) saves snapshots to a disk you own so you can undo accidents fast and keep sensitive data off any cloud service. Most pods want both.
      

      

        You can choose per-app — or per-folder — what's eligible for cloud. Cloud vs. local: tradeoffs →
      


      
      

        

          

            

              
Cloud backup

              

                Good for: recovering from drive failure, theft, or moving to a new mini.

                Costs: needs internet to back up; the operator's GitHub account hygiene is part of the security model; anything you don't classify as local-only lands on GitHub's servers.
              

            

            

              
Local backup

              

                Good for: undoing accidents fast; keeping sensitive data on hardware you own; protection from cloud outages or account loss.

                Costs: needs a disk or NAS you actually own; doesn't protect against fire, theft, or local hardware failure.
              

            

          

          

            Most pods run both. Use the Data tab to choose what stays local and what's eligible for cloud — per app, or per folder.

Picking a backup destination

          

            Two options work well for an Evolve pod:
          

          

            External SSD or HDD — plug a USB-C or Thunderbolt drive into the mini and pick it in Time Machine. Cheapest path. Backups run as fast as the drive can write; restores are fast too. Downside: a single drive means a single point of failure, and you have to remember to keep it plugged in.
            


            NAS (Synology / QNAP / etc.) — a network-attached storage box on your home network. Slightly more setup (you point Time Machine at an SMB share that supports TM), but the drive stays in a closet instead of dangling off the mini. Good if you want backups out of the way and want redundancy (RAID).
            


            Avoid: backing up Time Machine to the same physical drive the mini boots from. If the drive dies, both copies die.
          

        

      


      
      

        

          
What gets backed up where

This tab lets you decide, per app, which directories stay local-only and which are eligible for cloud — so sensitive data never leaves the mini even though backup is on.

                role's model comes from is decided in three layers, from most

                default, which overrides Evolve's built-in. On each bot tab you
                choose Use pod defaults (the bot inherits this
                tab's tier definitions, matched to the providers it has
                credentials for) or Custom (the bot defines its
                own model set).

                on a schedule rather than inside a bot — resolves its models from
                your primary bot. The Engine panels below are

      What Evolve does
      
          
      
            OpenClaw gives you powerful AI bots. Evolve answers the questions that come next:
            are they running, what are they costing, are they getting better, and how do you
            manage several of them without living in a terminal window?
          
      
          
      
            Think of it like this: OpenClaw is to AI assistants what Linux is to servers — capable
            and open, but requiring real effort to run well. Evolve is what Ubuntu is to Linux.
            We don't replace the underlying stack; we put wizards, dashboards, and a conversational
            interface on top of it so a household or small business can actually run it.
          
      
          
      
            Your data stays on your hardware. Every meaningful change goes through a human-approval
            step before it applies. The system watches constantly but acts conservatively.
          
      
        
      
        
      
          
      The pod model
      
          
      Layer 1: Your bots  (team_bot_a, admin_bot, team_bot_b...)
         Do the actual work. Each runs its own gateway.

Layer 2: evolve user  (the management layer)
         Runs this admin server, analysis jobs, security audits.
         Cannot be influenced by the bots it manages.

Layer 3: You  (pod-admin)
         Approve changes, manage keys, deploy updates.
         The only human in the loop.
      
          
      
            This separation is intentional. A bot can't reach up and change its own management layer.

      Step 1 — Enable HTTPS for your phone
      
            
      
              Unlike the desktop install, a phone install needs a secure
              context. Plain
              http://<tailnet-host>:5050
              gives no service worker, and iOS treats "Add to Home Screen" like a plain
              bookmark rather than a real app. The simplest fix is to let Tailscale serve
              the dashboard over HTTPS on your tailnet:
            
      
            
      # On the pod (Mac Mini), expose the dashboard over HTTPS on your tailnet:
tailscale serve --bg 5050

# Then open the https URL Tailscale prints (https://<your-pod>.<tailnet>.ts.net) on your phone.
      
            
      
              Without this, the icon may open as a regular browser tab instead of a
              full-screen app.
            
      
          
      

          
          
      Step 2 — Add to Home Screen
      
          
      
            With the HTTPS URL open on your phone, add it to your home screen. The guided
            steps cover both iOS Safari (Share → Add to Home Screen) and
            Android Chrome (⋮ → Install app).

      What the Continuity Engine does
      
          
      
            During a conversation, a bot might commit to deferred work: "I'll write that to memory tonight," "Remind me to check back in 20 minutes." Without the Continuity Engine, these evaporate when the session ends.
          
      
          
      
            The engine intercepts those commitments, turns them into structured tasks, queues them, and runs them at the right time — zero re-initiation required from you.
          
      
        
      
        
      
          
      Managing tasks
      
          
      # See what's queued
evolve-admin tasks list

# Approve a task
evolve-admin tasks approve <task-id>

      If a topic needs a full explanation rather than a tooltip, the badge or its surrounding section links to a deeper card on this page or one of the topic-specific Help docs.
      
              
      The pattern is intentional: keep the screens themselves clean of explanatory prose; let detail come on demand when the user wants it.
      
            
      
            
      
              
      
                
      Errors and Feedback (sidebar pages)
      
                
      Dedicated sidebar pages under Settings for reviewing captured errors and reporting issues.
      
              
      
              
            
      
            
      
              
      Errors — review all errors captured on this pod, grouped by unique signature so the same error doesn't appear 1,000 times. Acknowledge, mark as won't fix, or hand one to evo on the Feedback page for a deeper look.
      
              
      Feedback — chat with evo about anything bothering you. Pick an intent (Bug report / Feature request / Something else) or just start typing. Evo investigates, fixes what it can on the spot, and files a GitHub issue when it's worth tracking — you approve before anything is posted.
      
              
      Errors are kept locally by default. Nothing is sent upstream automatically — you review every issue body before evo posts it under your GitHub account.

      Core concepts
      
          
      
            
      
              
      
                
      Applications vs. Skills
      
                
      The difference between a skill (capability) and an application (goal-shaped contract).
      
              
      
              
            
      
            
      
              
      A skill is a capability primitive: "Read my Gmail inbox," "Send a Slack message," "Save a note to Obsidian." Skills come from the OpenClaw community.
      
              
      An application is a goal-shaped contract: "Morning Briefing" combines email + calendar + weather, delivered at 7 AM. Each application knows what it's supposed to deliver, and Evolve measures whether it does.
      
              
      Install skills from Skills; install applications from Apps → Gallery.
      
            
      
            
      
              
      
                
      Continuity Engine
      
                
      How deferred tasks are extracted from sessions, queued, and run autonomously (or with approval).
      
              
      
              
            
      
            
      
              
      If you tell a bot "check back in 20 minutes" or "write that to memory tonight," the engine intercepts those commitments at session end and runs them when the time comes.
      
              
      Simple tasks run automatically. Tasks that need judgment require approval via evolve-admin tasks approve <id>. A morning digest at 8 AM summarizes what ran overnight.
      
            
      
            
      
              
      
                
      Reporting a failure with evo fail
      
                
      Tell the bot something stopped working; it investigates and replies in the message thread.
      
              
      
              
            
      
            
      
              
      What it does. When something the bot is supposed to do quietly stops working, you can report it in plain language and the bot triages and diagnoses the failure for you.
      
              
      When to use it. Anything where you noticed an absence or a misbehavior — a scheduled message that didn't arrive, an app that used to respond and doesn't, a reminder that stopped firing. You don't need to know what's broken; just describe what you noticed.
      
              
      What to expect. Type evo fail <description> in any messaging channel the bot is in. You'll get an immediate “Looking into it” reply. The diagnosis arrives as a follow-up message, typically within a minute or two. The reply is short — the plain-language cause, one suggested fix, and a confidence rating. If the bot can't pinpoint a single cause it says so honestly rather than guessing.
      
              
      Escalating to the operator. If the diagnosis doesn't resolve your issue (or there isn't a clear diagnosis), reply evo fail flag. That creates a ticket in the operator's queue with the full investigation context attached — the operator picks up where the bot left off.
      
              
      Other forms: evo fail recent re-investigates your most-recent report; evo fail status shows where things stand. Rate limit: 3 investigations per user per hour so a flurry of reports doesn't overwhelm the system.
      
            
      
            
      
              
      
                
      Recommendations and the coaches
      
                
      How a dozen specialized coaches produce prioritized suggestions, and how approvals apply changes.
      
              
      
              
            
      
            
      
              
      The coaches aggregate signals from across your pod and turn them into a ranked queue of suggestions. Each carries a dimension, urgency, and a falsifiable claim ("this reduces gateway restarts ≥30% over 7 days").
      
              
      Approve → the system applies the change and verifies the claim. Dismiss → the coach records that feedback and adjusts. Security-critical items surface immediately, bypassing the weekly cap.
      
            
      
            
      
              
      
                
      How Evolve tracks the things your bot does on a schedule
      
                
      Scheduled actions — the recurring behaviors your bot is told to do at a specific time or interval.
      
              
      
              
            
      
            
      
              
      A lot of what a bot does day-to-day is recurring. "Post a protein tally at 6 PM." "Send a morning briefing at 7 AM." "Remind me on Sundays to check the calendar for the week ahead." These instructions usually live in the bot's heartbeat file or its standing-instruction files — not in code, not in cron, just in plain English the bot reads at the start of every session.
      
              
      The trouble is that those instructions can quietly disappear. A file gets edited and shortened. A section gets rewritten and the timing falls out. A deploy replaces the file with a fresh copy that doesn't include the section you added. When that happens, the bot just stops doing the thing — no error, no alert, you only notice when the reminders you were counting on don't show up.
      
              
      To catch that, Evolve's scanner now reads through the standing-instruction files looking for things that sound like a schedule (“every evening,” “6 PM daily,” “each morning”) and records each one as a scheduled action on the relevant app's manifest. Every six hours, the audit cross-checks those records against the files: if the section that described the behavior is gone, you get a finding on the Apps page telling you which behavior is missing and which file lost it.
      
              
      If you don't see scheduled actions on an app you'd expect them on, hit Re-scan on the Apps page. The scanner picks them up automatically the next time it runs.
      
              
      This is most useful for behaviors that live in the bot's heartbeat or AGENTS file — things the bot does because its standing instructions say to, not because there's a cron job or a script. Those are the behaviors that disappear most quietly.

      Set up GitHub token for issue tracking
      
          
        
      
        
      
          The inbox watcher polls GitHub for activity on issues you filed
          via evo intake promote, and the promote call itself
          uses this same token to create the issue. It needs a
          Personal Access Token to authenticate those calls.
          

      
          Pick a scope based on what you're tracking:
          
        
            
      • If any of your tracked repos are private
              (e.g. your own evolve-ops/evolve fork), use
              classic PAT with repo scope ▶.
              Without repo, classic PATs can't see private
              repos even when they own them — GitHub returns 404
              everywhere, which surfaces as "PAT scope too narrow" on the
              repo badge.
        • 
            
      • If you're only tracking public
              upstreams (e.g. openclaw/openclaw),
              classic PAT with public_repo ▶
              is enough and gives the watcher less reach.
        • 
            
      • Fine-grained PAT
              works too — explicitly include each tracked repo and grant
              Issues: read+write + Metadata: read.
